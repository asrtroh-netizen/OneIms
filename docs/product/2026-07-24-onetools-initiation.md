# OneTools 立项一页纸 · 产品规格草案

> 状态：立项草案 v0.2（**方向已拍板 · 方案 A**，未落地代码）  
> 日期：2026-07-24 · 拍板：2026-07-25  
> 视角：PM 产品经理（需求澄清 · MVP · 验收 · 指标）  
> 关联产品：OneIMS（Pixel IMS 配置 / 诊断 / 修复）· Telegram OneBoardX  
> 架构蓝图：`docs/architecture/2026-07-25-onetools-architecture-blueprint.md`  
> 采证：工作区无 `OneTools` 既有实现；用户确认「就是 OneTools，拍板方案 A」

---

## 0. 一句话

**OneTools** 拟作为 One 生态下的「工具层」品牌立项；与 **OneIMS（通信能力主产品）** 解耦，避免把更多非 IMS 能力继续塞进主 App。

---

## 1. 背景与问题（Why Now）

| 事实 | 含义 |
|---|---|
| OneIMS 主线已冻结对外最终版 **v3.0.2**（README） | 主产品语义清晰：IMS / 诊断 / 恢复；不宜无限加杂项工具 |
| 双产品线（OneKuku / OneIms Lite）差异在特权通道 | 品牌复杂度已高，再塞「万能工具」会稀释心智 |
| 仓库已有 `tools/`、大量诊断/对比脚本与 `.tmp_*` 工作流 | **作者侧工具能力**存在，但未产品化、未对用户形成统一入口 |
| 会员定价草案强调「核心免费、增值付费」 | 新立项需提前想清：免费引流 / 会员权益挂靠 / 独立变现 |

**用户痛点（待验证假设，非已证实）：**

1. 用 OneIMS 时，常需配套做：无线调试、日志、截图对比、配置备份巡检、设备信息汇总——分散在系统设置与多 App。  
2. 作者/进阶用户维护多机、多包、双产品线时，缺少「一站式小工具台」。  
3. 社区（Telegram）重复问答多属于「通用 Android 工具问题」，不宜继续堆进 IMS 主 App。

## 2. 定位方案对比（Innovate）

### 方案 A · 用户向「Pixel / Android 配套工具箱」（推荐候选）

| 项 | 内容 |
|---|---|
| 一句话 | 给 OneIMS 用户的**配套小工具 App**：配对助手、设备信息、日志导出、配置巡检等 |
| 目标用户 | OneIMS 现有用户 + Pixel 折腾党 |
| 与 OneIMS 关系 | **姊妹产品**；可深链互唤，不合并进主包 |
| 优点 | 心智清晰；保护 OneIMS 主线；可独立发版节奏 |
| 风险 | 需重新获客；功能若过泛变成「又一个工具箱」 |
| MVP 成本 | M |

### 方案 B · 作者向「内部工作台产品化」（偏内部）

| 项 | 内容 |
|---|---|
| 一句话 | 把仓库脚本 / 发版 SOP / APK 对比 / 抓包复盘做成**作者桌面或本地工具台** |
| 目标用户 | 你自己 + 协作维护者 |
| 与 OneIMS 关系 | 研发基础设施，可不对公发 App |
| 优点 | 立刻降你的操作成本；范围可控 |
| 风险 | 对用户无感知；不宜叫「立项」对外传播 |
| MVP 成本 | S～M |

### 方案 C · 平台向「One 生态统一工具品牌」

| 项 | 内容 |
|---|---|
| 一句话 | OneTools = 伞品牌：下属 IMS、Shizuku 修缮、诊断插件、脚本市场等 |
| 目标用户 | 全生态用户 |
| 与 OneIMS 关系 | OneIMS 降级为 OneTools 子产品之一 |
| 优点 | 长期品牌扩展空间大 |
| 风险 | **现在过大**；与现有 README/双包叙事冲突；L 级治理成本 |
| MVP 成本 | L（本期不建议） |

### 方案取舍（已拍板 · 2026-07-25）

| 优先级 | 方案 | 结论 |
|---|---|---|
| **已拍板** | **A** | 对外立项走 A：姊妹工具 App，MVP 只服务 OneIMS 用户最高频配套动作 |
| P1 可选并行 | **B 精简版** | 作者本地 CLI/桌面可作为内部加速器，不挡 A 对外主线 |
| 暂缓 | **C** | 等 A 跑通 1～2 个版本、命名心智稳定后再谈伞品牌 |

**拍板结论：方案 A。** 后续章节按 A 执行；不再写「默认假设」。

## 4. MVP 范围界定

### MVP In（必须做）

1. **独立应用壳**（`com.onetools.app`）+ **第一页 UI 直接移植 OneIMS `OneLinkHome`**（含四态 StatusHero）  
2. **配色与 OneIMS 一致**（复用 `OneImsTheme` / `OneImsTokens`，含 primary 白与动态色语义）  
3. **Shizuku 特权通道**（硬需求）：检测/引导安装与授权  
4. **一键导出诊断文本**（含四态与 Shizuku 状态；追加在原首页结构之后，不重排英雄区）  
5. **与 OneIMS 关系说明页**（姊妹产品，不替代 IMS 写配）  
6. **隐私边界声明**

### MVP Out（明确不做）

- 不实现 CarrierConfig 写入 / VoLTE 开关（仍归 OneIMS）  
- 不做会员支付闭环（可预留入口，不阻塞 MVP）  
- 不做插件市场 / 脚本商店（方案 C 能力）  
- **不做内嵌 OneBridge / 自研无线调试配对**（通道只走 Shizuku）  
- 不做 Root 提权实现（可检测/引导，不自研提权）  
- 不做 iOS / 非 Android  

### 边界场景（验收必测）

| 场景 | 期望 |
|---|---|
| 未授权短信/电话权限 | 摘要降级展示，不崩溃，文案说明缺什么 |
| 无 SIM / 双卡 | 明确空态；双卡分别列出或标注「未选卡」 |
| 未安装 OneIMS | 引导下载文案 + 仍可用设备摘要 |
| 导出超大日志 | 截断/分段 + 体积提示，避免 ANR |
| 用户拒绝存储/分享 | 取消路径干净，无残留半文件 |

## 5. 验收标准（MVP Definition of Done）

| # | 标准 | 可验证方式 |
|---|---|---|
| AC-1 | 冷启动 ≤ 2s 到首屏可用（中端机主观可接受） | 真机计时 |
| AC-2 | 首页 3 秒内看懂「这是 One 生态工具，不是又一个 IMS」 | 5 人冒烟口述 |
| AC-3 | 一键导出文件可被 Telegram 直接发送且作者能据此回答 80% 常规问题 | 用 3 份真实案例回放 |
| AC-4 | 从 OneIMS 深链（若本期接通）落到正确工具页；未接通则说明页可手点到达 | 联调清单 |
| AC-5 | 无写入运营商配置的代码路径（防范围漂移） | 代码审查 + 功能清单对照 |
| AC-6 | 中文主文案完整；关键危险操作有确认 | UI 走查 |

## 6. 数据指标与体验取舍

### 北指标（立项后 4～8 周）

| 指标 | 目标（草案） | 说明 |
|---|---|---|
| 激活后 7 日导出使用率 | ≥ 40% | 证明「取证」是真需求 |
| OneIMS ↔ OneTools 互唤成功率 | ≥ 90%（若做深链） | 姊妹产品体验 |
| Telegram「缺材料」往返轮次 | 下降 30% | 质性+抽检 |
| 1-star 中「乱收费/锁通话」提及 | = 0 | 范围红线 |

### 体验取舍原则

1. **窄而深 > 宽而浅**：MVP 宁可不做十个小工具，也要做好「摘要+导出+通道助手」。  
2. **本地优先 > 云同步**：降低隐私与合规成本。  
3. **引导 OneIMS，不替代 OneIMS**：文案禁止暗示 OneTools 能修 IMS。  
4. **信息密度克制**：首页避免仪表盘堆指标（与产品 UI 预算一致）。

## 7. 非功能与风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 与 OneIMS 品牌混淆 | 高 | 独立包名/图标/商店文案；关系说明页 |
| 范围膨胀成第二 IMS | 高 | AC-5 + Out 清单冻结 |
| 权限索取过多导致卸载 | 中 | 按功能渐进授权 |
| 商店政策（调试/无线调试相关） | 中 | 文案合规审查；能力以「引导系统设置」为主 |
| 维护带宽被双产品线挤占 | 高 | OneTools 发版节奏独立；MVP 后冻结功能 2 周观察 |
