# 配对逻辑对照：2.0.8 / 2.0.9 vs 现在（2.2.0 工作树）

## 结论（先说）

**2.0.8 / 2.0.9「配对好用」的本质：根本不在本 App 里配对。**  
当时整包走官方 Shizuku：一点「激活」→ `openShizukuApp` → 用户在 **Shizuku 自己的无线调试启动页**完成配对/启动 → binder 回来即就绪。

现在的复杂度来自 **2.1 起 OneKuku 内嵌 ADB + 通知栏六位码**（Phase4 OneBridge），不是 2.0.9 变差了同一条路。

## 对照表

| 维度 | 2.0.8 / 2.0.9 | 现在 OneKuku | 现在 OneLink |
|---|---|---|---|
| 通道 | 官方 `rikka.shizuku` | 内置 OneBridge + 内嵌 ADB | 官方 Shizuku（轻壳） |
| 配对入口 | 打开 Shizuku App | 通知栏 RemoteInput / 引导弹窗 / mDNS | 打开 Shizuku 管理器 |
| 本 App 是否收六位码 | ❌ | ✅ | ❌ |
| Wi‑Fi / 热点前置 | 由 Shizuku 处理 | App 内 STA 等待、热点说明 | 交给 Shizuku |
| 已配对再开 | Shizuku 内点 Start | 无码直连 + tcpip:5555 | Shizuku 内点 Start |
| 代码体量 | `ShizukuSetupHelper` + `ShizukuManager` | EmbeddedAdb / MiniAdb / Mdns / PairingNotification… | `openShizukuManager` + 门禁 |

## 分叉点（git）

- `e7f6923` / `843f44c`：嵌入通道 + 通知栏配对（离开 2.0.9 模型）
- 之后：双路径、Wi‑Fi 前置、九态/五态卡、tcpip 开/关、常驻服务等叠层

## 建议

1. **OneLink**：保持 = 2.0.8/2.0.9 体验（已基本对齐）；勿再加内嵌配对。  
2. **OneKuku**：若觉得「配对难用」，应对照 2.0.9 简化**首次**路径（少弹层、通知栏填码即走），而不是整段回滚到外置 Shizuku。  
3. 不要把两线配对 UX 揉回同一套。
